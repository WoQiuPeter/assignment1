## 1:00–3:15：重复添加与库存边界——先测试，再实现

屏幕：`test/cart.test.js` 的 `addToCart / 添加商品`，随后切 `src/cart.js` 的 `addToCart`。

“先看重复添加这个测试。测试目录里 A 商品库存是三，单价是一百二十分。第一次添加一件，再添加两件，最终应该只有一行，数量是三，而不是出现两行相同商品。这个断言同时检查了编号、数量和数组结构。

接着看累计超库存的测试。购物车先有两件，再添加两件，总数会变成四，大于三。这里应该报库存不足，而且购物车原来的两件必须保留。我在操作之前复制状态，报错后比较整个状态，检查的就不只是有没有抛出错误，还包括有没有错误修改数据。

现在切到实现。首先检查数量，然后查商品是否存在，再寻找购物车里有没有这一行。newQuantity 是原数量加上本次增加量。没有原商品行时，原数量按零处理。

库存检查针对的是累计数量，而不是只检查这次增加的数量。只有通过所有检查后，才会修改现有行，或者 push 一行新商品。每行都包含 productId、quantity 和 totalPrice，合并数量时也同步更新小计。因此库存错误发生时，原车保持不变。

边界测试还验证了恰好添加三件可以成功，库存零的商品不允许添加。上限条件写的是大于库存，所以等于库存仍合法。”

操作：指向累计计算、库存判断和两个修改分支，停留让观众看清。

## 3:15–4:45：非法数量——业务校验与输入校验

屏幕：添加商品的 `it.each`，随后 `checkQuantity`；再看 `src/cli.js` 的数量解析。

“数量不只是检查正负。我还测试了零、小数、NaN、Infinity、字符串和超过安全整数范围的数字。业务函数用 Number.isSafeInteger 检查类型与整数范围，再要求数量大于零。这样不能把字符串二当成数字二直接传进来。

终端收到的输入一开始全是文本，所以命令层要先检查格式。我用正整数的完整匹配规则，再转换为 Number，最后由业务函数检查安全整数。

这里没有直接用 parseInt，因为 parseInt 可以把二后面跟字母的文本解析成二，也可能把小数截断。我的选择是明确拒绝错误输入，避免用户输入和实际购买数量不一致。

输入错误会抛出带说明的错误，由终端循环捕获和显示。业务函数不负责打印提示，因此测试时可以直接验证错误，不需要模拟键盘。”

## 4:45–6:15：修改、删除和清空

屏幕：`updateQuantity` 测试，然后对应实现；简要展示删除与清空测试及函数。

“add 和 set 的含义不同。add 是增加量，set 是最终目标数量。例如已有两件，设置成一件，结果应该是一件，不能变成三件。这个测试先加两件再改成一件，还检查可添加数量从一变回二。

实现里同样先检查数量和商品，再确认购物车确实包含这一行，检查目标数量没有超过库存后，同时更新 quantity 和 totalPrice。测试也检查这两个字段同步变化。这里数量零不代表删除，删除使用独立命令。修改、删除和清空是题目基础操作之外的简单附加功能。

删除测试同时放入两种商品，删掉 A 后 B 应该保留。实现用 filter 保留编号不匹配的行。删除不存在的行会报告错误，让用户知道操作没有完成。

clear 直接把商品行数组清空。因为加车时没有扣实际库存，所以清空不需要把库存加回去。否则反而会把库存增加到初始值以上。我也测试了重复清空空车，结果仍然是空车，不需要报错。”

## 6:15–8:15：金额计算与数据结构

屏幕：`getCartSummary / 金额计算` 的完整摘要测试，然后 `getCartSummary` 实现。

“这个测试的答案可以手算：A 每件一百二十分，买两件是二百四十分；B 每件二百五十分，买一件。总数是三件，总金额四百九十分，也就是四元九角。

断言里直接写了这些预期值，没有再调用被测函数计算答案。否则如果同一种计算方式有问题，测试可能跟着得到同一个错误结果。

实现先用 map 把每个购物车项转换成一行摘要，带上商品名、单价、数量和已有的 totalPrice；再把各行小计转换为整数分，用 reduce 累加。reduce 的初始值是零，所以空车总金额也是零。

购物车项按题目保存编号、数量和行小计，不重复保存名称与单价。单价从商品目录查；添加和修改数量的函数负责维护行小计。items 本身是数组，外面用会话对象把它和独立商品目录放在一起，方便隔离测试。

另一个测试用零点一元和零点二元得到三十分。直接累加小数会有二进制表示误差，所以我用 toCents 把元转成整数分。它也检查价格不是负数、最多两位小数且在安全范围内。行小计计算完成再转回元保存，累计总价时再转换成整数分。toFixed 只负责显示两位小数，不能替代正确计算。

返回的摘要是一份新对象。测试修改摘要数量，再检查原购物车没有变化，目的是避免外部代码只是准备显示数据，却意外修改购物车。商品目录在创建时也复制了一份，使不同测试之间不会互相影响。”

## 8:15–10:30：结账与错误时状态完整

屏幕：`checkout / 结账` 的正常测试、整单失败测试，然后 `checkout` 实现。

“结账是主要操作，因为它同时涉及金额、库存和购物车内容。正常测试放入 A 两件和 B 一件，检查收据是四百九十分、三件商品；A 库存从三变成一，B 从二变成一，购物车清空。

空车结账会报错。成功结账后会清空购物车，CLI 随即结束。单元测试仍可以直接检查业务对象的库存和空车状态；这是函数层面的验证，不表示终端会继续接受输入。

我重点看一下最后这个测试。它先加入两种商品，再把后一个商品的库存改低，模拟结账前库存状态变化。预期整张订单失败，并且 A 也不能提前扣库存。这是为了检查错误不会只完成一半。

实现先拒绝空车，并生成摘要；然后第一个循环检查每种商品的数量和库存。全部通过后，第二个循环才扣库存。最后清空并返回刚才生成的收据。

如果把校验和扣库存写在同一个循环，可能第一件已经扣了，第二件才发现库存不足。这里分成两个循环，是为了让修改发生在所有校验完成之后。

这个方案适用于当前单进程、同步的内存数据。它不是数据库事务，也不能解决多个用户同时抢库存的问题。如果以后接数据库或多人系统，还需要由数据库保证库存更新的完整性。”
